# Vacation Memories Editor — Specification of the interactive editor (UI)

Status: **approved** (decisions closed on 2026-11-14, section 16; `SPEC.md` updated, section 17). It extends `SPEC.md`: `SPEC.md` describes the application, the CLI and the containers, with short references to the editor; this document describes the editor in detail. The two must stay consistent.

Visual reference: `docs/ui-mockup/` (board "Layout B - lightweight", 1440×900, plus the screenshots). The mockup works on fake data, is HTML written for a design editor and **is not code to copy**. It is kept only locally (ignored by git), so everything normative is written here: the mockup is the reference only for the look (layout, spacing, components) of what this document does not describe in detail. Behavior is only what this document says. The mockup shows a "Video audio" lane that is not built (D5).

## 1. Goal

A local web application that drives the whole job: choose the input folder, set the options and run the analysis when it is missing, review the selected moments and a preview, optionally edit the final timeline, render the video. It replaces the CLI for everyday use and the hand editing of `edit_plan.json`, and absorbs "Milestone 4 — Review".

The editor is a front end, not a second implementation: analysis, planning and rendering are the existing CLI, run as child processes on the same files (section 6). The CLI stays complete, and a project can be continued from either of them.

It is not a generic video editor: it works only on what the plan can express and the renderer can produce. A feature without an equivalent in the plan and in the renderer is not built, not even hidden.

## 2. User flow

1. **Start.** The launcher (step U8, D15): a double click opens a Google Chrome `--app` window that asks the folders on the first start, starts the containers and shows the editor; closing the window stops them. Or `docker compose up -d editor nginx`, then the browser at `http://127.0.0.1:8080`.
2. **Input folder.** The folders under the media root (`MEDIA_DIR`, mounted at `/media`), with the number of photos and videos and the state of their project: not analyzed, analysis incomplete, analyzed, plan edited, video rendered. Choosing a folder opens its project, or creates it (section 5). Subfolders are included, as in the scanner.
3. **Settings and analysis**, only when the analysis is missing or incomplete (new or changed files, interrupted job). The settings screen (section 7), then "Analyze": a job with progress (section 6) that ends with the plan already generated. If the analysis is complete, the flow goes straight to step 4. The settings stay reachable from the top bar.
4. **Review.** The timeline with the selected moments; the Media panel with every candidate, selected, not selected and discarded; the preview of the whole video, rendered in low resolution by a job that starts by itself after every new plan (it can be stopped).
5. **Editing** (optional). Sections 10–13.
6. **Rendering.** "Export video" starts the final render (section 6). At the end the editor shows where the file is (path relative to `WORK_DIR`) and offers it for download.

Going back: a change of the settings that alters the plan (duration, structure) regenerates it, after a confirmation, with a backup of the previous plan and the exclusions carried over (section 5). Resolution and aspect change only the rendering, as in `SPEC.md`, and do not regenerate the plan.

## 3. Constraints inherited from SPEC.md

- **Everything in Docker containers**, in development and in use. The interface is a **local web page** opened in the host's browser. No native window, no dependency on `DISPLAY` ("Headless execution" in `SPEC.md`). The server never opens a browser: the launcher does it, on the host, with a Google Chrome `--app` window (D15).
- **On the server without a display** the editor is reached through an SSH tunnel (`ssh -L 8080:127.0.0.1:8080 <server>`): the port is published only on the server's `127.0.0.1`.
- **No network**: the application makes no connection except the one to Ollama on the internal network, and the page **loads no external resource**. No Google Fonts and no CDN: fonts, scripts and icons are in the image, with compatible licenses (e.g. IBM Plex and Bricolage Grotesque, OFL). Icons are SVG: `.dockerignore` excludes `*.png` and the other media extensions from the build context.
- **Privacy and development data**: development and tests on synthetic media only. `MEDIA_DIR` stays `./dev-media`, which may hold several synthetic vacations as subfolders (generated by `evaluate/synthetic_media`). Claude Code does not open or list the folders with real media, nor the thumbnails, previews, plans and candidates generated from them (`<project>/ui/`, `candidates.json`, `eval/`). The trial on real data is up to the user.
- **Untouched originals**: media and music are mounted read-only; the editor writes only in the projects' workdirs.
- No new frameworks, libraries or services without a concrete reason ("How to work" in `SPEC.md`); every one of them is a decision of section 16.

## 4. Architecture

```
browser (host) ──► nginx ──────────────────► editor ─────────────► ollama
                   networks frontend          network backend      (backend + egress)
                   + backend                  (internal)
                   port 127.0.0.1:8080        ├─ JSON API (/api/…)
                                              ├─ static files of the interface
                                              └─ jobs: child processes `python -m vacation_memories …`
```

- **`serve` subcommand** of the existing CLI: `python -m vacation_memories serve`. Code in the `vacation_memories/editor/` subpackage (`server`, `projects`, `jobs`, `catalog`, `media` for thumbnails, waveforms and per-clip previews). The server serves the built interface from `vacation_memories/editor/static/`, which exists only in the image (see "Frontend").
- **HTTP server from the standard library** (`http.server.ThreadingHTTPServer`), consistent with "Stack" in `SPEC.md` (no HTTP library). Single-range `Range` requests are implemented for the video files, which the browser's `<video>` element needs for seeking. Progress by polling every second, no SSE (D8).
- **Jobs** (analysis and plan, preview, export) are **child processes of the existing CLI** (section 6): each one takes the project's workdir lock, writes `status.json` and its log as today. The server does not take the lock and only reads `status.json`. One job at a time in the whole editor: the machine is shared with Ollama. On SIGTERM the server stops the child's process group in an orderly way, within the time of "Signals, SSH sessions and resumes" in `SPEC.md` (target 5 s).
- **`nginx`** is the only service on two networks: `frontend` (new, an ordinary bridge with nginx only) and `backend`. It publishes only `127.0.0.1:8080`. It is a pure reverse proxy: no volumes except its configuration (`docker/nginx.conf`, read-only), it serves no files and logs no query strings. Unprivileged image with a pinned tag (e.g. `nginxinc/nginx-unprivileged`), `read_only` with a tmpfs for its temporary folders, `cap_drop: [ALL]`, `no-new-privileges`. Reason: an `internal: true` network cannot publish ports, and `editor` must stay without Internet access like `app`.
- **`editor` service**: the `runtime` image of `app` with the `serve` command, the same hardening (user, `init`, `read_only`, `cap_drop`, `no-new-privileges`, `stop_grace_period: 30s`) and the same volumes (`/media` and `/music` read-only, `/work`, `docker/compose.toml`). Only on `backend`. **No `depends_on` on `ollama` or `ollama-pull`**: the editor starts and works with Ollama stopped, and checks it only when the user chooses the analysis with AI. A healthcheck on `/api/health` lets the launcher wait for it.
- **The editing rules live in Python, in one place**: `planning/plan_rules`, built on `planning/transitions` (`layout_timeline` stays the only layout and duration function, shared by planner, renderer and editor). The interface does not reimplement them: it receives from the server the **limits** of every element (minimum and maximum duration, free intervals for the transitions, bounds of the moments, range of the music shift) and uses them for immediate feedback while dragging. The server **always recomputes and rechecks** on save. So the rules are tested with `pytest`.
- **Frontend** (D7, D10, D11): React and TypeScript, sources in `frontend/` (`package.json`, `package-lock.json`, `tsconfig.json` with `strict`, `src/`). Bundled with esbuild and type-checked with `tsc --noEmit`. Exact versions in `package.json`, installed with `npm ci` from the lockfile, licenses compatible (React is MIT). Plain CSS with the tokens of section 10, fonts and icons bundled from the repository.
  - **Build**: a Node stage of the Dockerfile (pinned image) runs `npm ci` and the build; the `runtime` stage copies only the bundle into `vacation_memories/editor/static/`. **Node is never in `runtime`.** The bundle is not committed: `frontend/dist/` and `frontend/node_modules/` go in `.gitignore` and `.dockerignore`. After a change of the frontend, `docker compose build editor`, as for `app`.
  - **Development**: a `ui-dev` service in the `dev` profile, on the same Node stage, with the repository mounted, for `npm run check` (`tsc`) and `npm test`. As in `dev`, the dependencies are installed in the image (outside the mounted folder) and change only by rebuilding it; `ui-dev` has no network and nothing is installed on the host.
  - **Types**: the plan v2 and the API in one module (`frontend/src/api/types.ts`), checked against JSON fixtures of plans shared with `pytest` (`tests/fixtures/`).
  - **Language**: Italian by default, texts in language catalogs (D10).
- **Undo/redo**: on the client, snapshots of the plan (60 steps). The server keeps no history; it saves the plan at every confirmed change.

## 5. Projects and files

- A **project** is an input folder (relative to the media root) with **its own workdir**, `/work/projects/<slug>-<hash>/`: the slug comes from the folder name, the hash from its relative path, so two folders with the same name do not collide. One workdir per input, because cache, plan, `run_config.json` and lock belong to the workdir and the cache key is the path relative to `--input` (D9).
- The CLI works on the same project with `--input /media/<folder> --workdir /work/projects/<id>`. A CLI job on a project where the editor is running one exits with code 5, as today, and the editor shows the project as busy.
- Files of the project workdir: the existing ones (`cache.sqlite3`, `edit_plan.json`, `run_config.json`, `status.json`, `render_report.json`, `runtime_profile.json`, `run.log`, `segments/`, `tmp/`) plus:
  - `project.json`: input folder (relative) and settings (section 7), written atomically by the server;
  - `candidates.json`: written atomically **by the pipeline** after every analysis (`--analyze-only`, `--dry-run`, full run): the analyzed files (relative path, size, mtime) and every candidate with its id, type, source, `start`/`end`, scores (`final`, `technical_score`, `narrative_score` and components), `moment_type`, `category`, day, duplicate group and representative, discard reason (black, blurry, duplicate, …). The catalog reads this file: the server never reruns the analysis or the ranking and does not open `cache.sqlite3`;
  - `plan_history/`: copies of the plan taken before every regeneration (the last 10);
  - `ui/thumbs/`, `ui/waveforms/`, `ui/clips/`: caches of thumbnails, waveforms and per-clip previews, regenerable;
  - the videos: `<name>_preview.mp4` (preview) and `<name>.mp4` (export), default name `memories`.
- **"Analysis present"**: every readable media file of the folder is in `candidates.json` with the same size and mtime. Otherwise the analysis is incomplete and the editor offers to complete it (the cache makes the files already analyzed immediate). The AI coverage is reported apart: a time budget can leave it partial by design.
- **Plan regeneration** (full run or `--dry-run` from the CLI, or a change of the settings in the editor): if the existing plan contains user edits (`origin: user`, `duration_origin: user`, effects with `origin: user`, `excluded`, changed music), before overwriting it the pipeline copies it into `plan_history/` and passes `excluded` to the planner, which does not select those moments again. The editor asks for a confirmation first. This rule applies to the CLI too.
- No absolute host path in the API responses: paths relative to the media root and to the music root, and opaque ids.

## 6. Jobs

| Job | Child process (CLI) | When |
|---|---|---|
| Analysis and plan | `--dry-run` with the project's options: `--input`, `--workdir`, `--duration`, `--structure`, `--aspect`, `--resolution`, `--assume-tz`, `--ai-time-budget` or `--ai-frames`, and `--require-ai` or `--no-ai` | after the settings of a new project; after a change of duration or structure; "Complete the analysis" |
| Preview | `--render-only --preview --output <name>.mp4` (writes `<name>_preview.mp4`) | by itself after every new plan (setting, on by default); "Full preview" |
| Export | `--render-only --output <name>.mp4` | "Export video" |

- `--dry-run` already does the analysis (reusing the cache) and the plan, so no new pipeline mode is needed.
- **AI**: before a job with AI the server checks Ollama as `doctor` does (reachable, model present). If it is not available the user chooses between waiting (e.g. model still downloading) and the analysis without AI. With AI the job gets `--require-ai`, so it never produces a result without AI silently; without AI it gets `--no-ai`. Review, editing and rendering never use the AI.
- **Progress**: `GET …/status` returns `status.json` (phase, items done and total, remaining time, state) plus the job type and, at the end, its exit code.
- **Stop**: SIGTERM to the child's process group, orderly shutdown with code 143. Running the same job again resumes it: the cache and the finished segments are reused.
- **The plan while a job runs**: during "Analysis and plan" it is read-only (a `PUT` gets 409). During a render it can be saved, with a warning that the render uses the version read when it started.
- **Exit codes** shown as messages: 0 done; 2 invalid settings or plan, with the message; 3 final check failed (the `.partial.mp4` stays, as in `SPEC.md`); 4 missing requirements (FFmpeg, space; Ollama or model with AI); 5 project busy; 130/143 interrupted, resumable.
- **Per-clip previews** are not jobs: short FFmpeg runs of the server itself (same runner: `-nostdin`, process group), one at a time, that read only the media and write only in `ui/clips/`. They do not take the lock and do not write `status.json`.

## 7. Settings

Shown before the first analysis and reachable later from the top bar. Every field corresponds to a CLI option, with the same validation and error messages; the interface adds none.

- **Analysis**: AI yes or no (default yes if Ollama and the model are available, otherwise no, with the reason); AI time budget (`--ai-time-budget`, default 600 s), or an exact number of frames (`--ai-frames`, under "Advanced"); assumed time zone for the `mtime` fallback (`--assume-tz`, default `ASSUME_TZ` of the compose file). The model is shown but not chosen: it is `OLLAMA_MODEL` of the compose file, the one `ollama-pull` downloads.
- **Edit**: duration (`--duration`, same formats and limits, default 5:00), asked before the analysis because it sizes the AI budget; structure (narrative or chronological); aspect; resolution; music (tracks from the music root, optional).
- **Advanced** (collapsed): `--jobs`, `--hwaccel`, `--nice`.
- **What each change requires** (as in `SPEC.md`): model or AI → AI analysis again (cache); duration or structure → new plan (regeneration, section 5), no analysis; resolution or aspect → only the `output` of the plan and the rendering; music → only the `music` block of the plan.
- Saved in `project.json`. The child process receives them as CLI options, which take precedence over `docker/compose.toml` (precedence of "Headless execution" in `SPEC.md`).
- The `[selection]` table of the configuration file is not exposed: it stays an expert setting in TOML.

## 8. Data model: `edit_plan.json`, schema 2

The plan moves to **`schema_version: 2`**. A v1 plan is migrated when read and rewritten as v2 at the first save; any other version is rejected (code 2), as today.

| Editor | Plan v2 |
|---|---|
| Sequence of the timeline (photos and moments in order) | `elements`, as today, in playback order |
| Identity of a clip (selection, undo, URLs) | `id` in every element, unique in the plan: the candidate id for the planner's clips, `user-<n>` for those added by the user. It does not change when the clip is trimmed |
| Photo with a changed duration (1–30 s, step 0.1 s) | `type: photo`, `duration` + `duration_origin: planner\|user` |
| Trimmed video moment (start, end) | `type: video`, `start`, `end`; the duration is `end − start`, as today |
| Moment added by the user (click on the video bar, ~6 s) | the same element, `origin: user` (default `planner`) |
| Deleted moment / hidden photo | `excluded: [ { source, start, end, reason: "user" } ]` at plan level (`start` and `end` null for a photo). Read by the planner when it regenerates the plan; ignored by the renderer |
| Music tracks (order, cuts, mute, fades) | `music: { tracks: [ { file, parts: [ { start, end, muted, fade_in, fade_out } ] } ], offset }`; `file` relative to the music root; the times of `parts` relative to the track |
| Music shift (positive = starts later; negative = skips the beginning) | `music.offset` in seconds |
| Transitions on the clips | `effects: [ { id, type, offset, duration, origin } ]` **in the clip**, `offset` from the start of the clip; `type`: `fade_in` (from black), `fade_out` (to black), `dissolve`, `dip` (to black and back, D1) |
| Dissolve between A and B | one effect only, `dissolve` in B with `offset: 0`, the meaning of `transition_in` in v1. "Dissolve at the end" of A writes it in B (D4) |
| Fade from black at the start and to black at the end of the video | `fade_in` effect of the first clip and `fade_out` effect of the last one, written by the planner with the configuration defaults (1 s and 3 s). No longer global for v2 plans (D4) |
| "Hard cut" | no dissolve at that boundary (it is not an effect) |
| Requested duration (5:00), output | `requested_duration`, `output`, as today |

Notes:
- **Migration v1 → v2**: the `transition_in` of B becomes a `dissolve` in B with `offset: 0` and `origin: planner` (the 25% limit stays, D3); the global fades become the effects of the first and last clip, with the configuration values; the `id` comes from `source` and the extent; `music` is absent (the `--music` of the command line still applies). The rendering of a migrated plan is the same as today.
- **Music fade-out at the end**: the duration of the final `fade_out` effect if present, otherwise the configuration default (section 9 of `SPEC.md`, "in sync with the music's fade-out").
- No `audio` block in v2: the original audio of the clips comes with Milestone 3 (D5).
- All times in seconds, with a tenth of a second of precision for the user's edits; the renderer rounds to frames.
- The plan stays **hand-editable** and renderable with `--render-only`, and the loading stays strict (unknown keys → code 2): the limits computed for the editor are never written into the plan, they travel next to it in the API.

## 9. API

All under `/api`, JSON. `{p}` is the project id.

| Method | Path | Use |
|---|---|---|
| GET | `/health` | The editor responds (healthcheck, launcher) |
| GET | `/ai` | Ollama reachable and model present, as `doctor` |
| GET | `/folders` | Folders under the media root (relative paths), number of photos and videos, state of the project |
| POST | `/projects` | Opens or creates the project of a folder; returns its id |
| GET | `/projects/{p}` | State: settings, analysis (files analyzed out of total, new or changed files, AI coverage), plan present or edited, preview present or outdated, exported videos, running job |
| PUT | `/projects/{p}/settings` | Saves the settings; errors with the field |
| GET | `/projects/{p}/plan` | Current plan, `revision` and `limits` (an object next to the plan, keyed by element and effect id) |
| PUT | `/projects/{p}/plan` | Saves the whole plan. Requires `If-Match: <revision>`; returns the normalized plan, the limits and the warnings. Validation errors with message and field path. Atomic write. 409 with an outdated `revision` or during "Analysis and plan" |
| GET | `/projects/{p}/catalog` | From `candidates.json` and the plan: photos (groups by score, duplicates grouped, hidden, discarded), videos with their moments, transition library, tracks of the music root |
| GET | `/projects/{p}/thumb/{media}` | Thumbnail (`ui/thumbs/`, cache) |
| GET | `/projects/{p}/waveform/{track}` | Peaks of the waveform of a music track (`ui/waveforms/`, cache) |
| GET | `/projects/{p}/clip/{element}` | Low-resolution preview of one element (`ui/clips/`, cache), with `Range` |
| POST | `/projects/{p}/jobs` | Starts a job (`plan`, `preview`, `export` with the file name); returns its id; 409 if a job is running |
| GET | `/projects/{p}/status` | `status.json`, job type, exit code at the end |
| POST | `/projects/{p}/jobs/cancel` | Orderly stop |
| GET | `/projects/{p}/video/{name}` | Preview or exported video, with `Range`; download with `Content-Disposition` |

Rules:
- **Only requests from the editor's own page**: the server checks `Host` (`127.0.0.1:8080` and `localhost:8080`, configurable for a tunnel on another port), checks `Origin` on every non-GET request and requires `Content-Type: application/json`; no CORS headers. This protects against other web pages open in the same browser (DNS rebinding, cross-site POST).
- The server **does not trust** the limits sent by the client: it recomputes them.
- No absolute host path in the responses. Media and clips are named by **opaque ids** (a hash of the relative path or of the element id), so file names end up neither in URLs nor in the nginx logs.
- One editor at a time on the same plan; `revision` prevents overwrites from another tab.

- Text never below **12 px**.
- Normal controls **36 px** tall; click areas of **44 px** for list rows, thumbnails and round play buttons.
- Every action that needs a drag has a **single-click or keyboard alternative** (sections 11 and 12).

## 11. Media panel (tabs)

**Photos**
- Photos grouped by interest score, which is `score.final` (0–1) of the candidate (collapsible groups, "Collapse all" / "Expand all"). Below them a collapsed "Discarded" group with the reason (black, blurry, duplicate): the user can still add them.
- **Interest threshold** slider (0–1): the photos below it are dimmed and announced as such. It does not hide them.
- Thumbnail with the score, the indicator of the grouped similar photos (×N), the "already in the timeline" mark and a button to **hide** the photo (it goes into `excluded`, with a "hidden photos" list and restore).
- Added to the timeline by dragging the thumbnail, or from the Detail panel with "Add to timeline". "Add all" per group.

**Videos**
- Collapsible rows. Every video shows a bar with the **moments** found (its candidates).
- **Click on a free point** of the bar: adds a moment (~6 s, `origin: user`).
- **Dragging the edges** of a moment changes its start and end (limits: inside the video, without overlapping the neighboring moments, at least 1 s; also with the arrow keys).
- A moment is dragged onto the timeline; a whole video is dragged to add all its moments not yet used.
- **Deleting** a moment also removes it from the timeline (it goes into `excluded`); "Restore deleted moments".

**Transitions** (library)
- Hard cut (removes), Dissolve, From black, To black; default durations from the single configuration (today 0.8 s, 1 s and 3 s), plus Dip to black (D1).
- They are **dropped on a clip** in the timeline (section 12). Click alternatives: selecting a clip shows the buttons "From black at the start", "Dissolve at the start", "Dissolve at the end", "To black at the end"; selecting a library transition, the "Apply…" button puts it wherever it makes sense (dissolve between all clips, From black on the first, To black on the last, Hard cut removes all dissolves).

**Music**
- The tracks of the music root with their duration and the "In the video · N" mark. They are **dragged** onto the music lane. "Restore deleted", "Add tracks" (chooses files of the music root).

## 12. Timeline

**Structure and scale.** Two lanes on the same time axis: *Photos and videos* and *Music*. Visible window `WIN = max(90, ceil((total + 5) / 10) × 10)` seconds; ticks every 10 s (20 s if `WIN > 150`). **Zoom 1×–6×**; above 1× a horizontal scrollbar appears; ‹ › buttons to scroll; the lane labels stay fixed. The **ruler** is clicked or dragged to move the playhead (also with the arrow keys, ±1 s, Shift ±5 s).

**"Photos and videos" lane**
- Clips are laid out in sequence. They are **reordered by dragging** (insertion mark) and added by dragging from the Media panel.
- Duration of a **photo**: two handles (visible only with the photo selected), 1–30 s, step 0.1 s; arrows ±0.1 s (Shift ±1 s); alternatively the "Duration" slider in the Detail panel.
- Duration of a **video moment**: not changed here, it follows from the trim of the moment (Videos panel or Detail).
- Empty: message "The timeline is empty. Drag photos and moments here from the Media panel."

**Transitions as overlays on the clip** (in the upper band of the clip)
- Position (D1): `fade_in` and an incoming `dissolve` at the start of the clip, `fade_out` at the end, a `dip` anywhere. An effect dropped elsewhere snaps to the nearest allowed position. A `dissolve` dropped at the end of a clip is written in the next one (D4).
- Limits (D3): an effect does not leave the clip, does **not overlap** the other effects of the same clip, lasts **at least 0.2 s** and at most the free space; a dissolve must fit in the free space of both clips it joins. The planner's transitions keep the 25% limit of `SPEC.md`.
- They **move by dragging**, also onto another clip (the position is recomputed in the nearest allowed free space); arrows ±0.1 s.
- With the transition selected two **handles** appear (start and end), and in the Detail panel the "Duration" and "Starts at" sliders.
- If a clip gets shorter the transition shrinks by itself; below 0.2 s it is removed, with the "Element removed · Undo" notice.
- Removal: "Remove transition" button, Delete key, or dragging "Hard cut" onto it.
- **Clarifications (U6)**: a boundary has one transition, so putting one where another is replaces it (a `fade_in` or a `dissolve` at the start of a clip replace each other, a `dissolve` also takes the `fade_out` of the clip before, a `fade_out` takes the dissolve into the next clip); a `dissolve` dropped on the first half of a clip joins it to the clip before, on the second half to the next one; a click alternative for the `dip` ("Dip to black here") puts it at the playhead when it is on the clip, in the middle otherwise; the library lists "Hard cut" first, and "Apply" has nothing to do for the `dip`.

**"Music" lane**
- The tracks are laid out in sequence and are dragged by their name to change their **order**; every track is **cut** at the playhead into parts, with mute, fade-in and fade-out, and "Delete part" (the following ones shift; if it was the last part, the track leaves the video).
- **Shift**: by dragging the body of a part, with the arrows ±0.1 s (Shift ±1 s), or with the "Shift" slider in the Detail panel; "Move the music back to the start". The value is `music.offset`.
- **Limits and clarifications (U6)**: a part lasts at least a second (`limits.music.min_part`, checked on save like the rest) and its two fades fit in it; the "Add tracks" button of the Music tab adds every track of the music root that is not in the video, and each row has its own add button; "Restore deleted" puts back, as parts, the stretches of the tracks in the video that no part covers (the plan keeps no record of what was deleted, so this is what it can tell); a track that leaves the video (its last part deleted) comes back with the add button.
- **Beyond the end of the video**: the music stays visible, dimmed, after the "end of video" line; **in the export it is cut** at the end of the video with the final fade-out (section 8). "Show all the music" button to see the whole tracks.

**Undo / redo and notices**
- Undo and redo cover every change to the plan (clips, durations, trims, exclusions, music, transitions), 60 steps; several changes in the same gesture (a drag, a slider) count as one.
- After a removal a notice appears at the bottom, "Element removed · Undo", for 7 s.
- Not undone: selection, zoom, playhead position, open tabs, settings (which have their own confirmation).

**Shortcuts** (when the focus is not in a text field): Ctrl+Z undoes; Ctrl+Shift+Z or Ctrl+Y redoes; Space starts and stops playback; Delete or Backspace removes the selected element; arrows on the selected handle or bar move it by 0.1 s (Shift 1 s).

## 13. Detail panel and preview

It changes with the type of the selected element: photo, video, moment, music part, track, transition (from the library or on the timeline), whole timeline. It shows: preview, scores (interest = `final`, narrative, technical), information, specific controls and actions (sections 11 and 12), with a help text explaining the effect.

**Whole timeline** (no selection): current duration against the requested one (`mm:ss of 5:00`, computed by `plan_rules`, D2), number of photos and moments, transitions, music, format; job progress; "Full preview" and "Export video".

**Preview.** In the mockup it is simulated. In the real editor:
- single clip: low-resolution preview generated by the server (`/clip/{element}`, in `ui/clips/`, cached), played with the browser's video element;
- whole timeline: the Preview job (`--preview`: short side 540 px, 24 fps), started by itself after every new plan. After an edit it is marked **outdated**, with "Update preview". It is not real time, and the button says so.

The playhead follows the actual playback; the mockup's playhead running without video is a simulation.

**Clarifications (U7).**
- **The preview of the whole video** starts by itself when the analysis job that makes a plan ends well, if the `auto_preview` setting (a project setting in `project.json`, on by default, in "Edit" of the settings, no CLI option) is on and nothing else is running. "Full preview" and "Update preview" in the summary start it by hand. It is marked outdated when the plan on disk is newer than the video or when the plan changed since the revision the preview job started from (the job records `plan_revision`, so a plan saved during the render counts); the mark is in the top bar and in the summary.
- **The export** is the "Export video" button of the top bar (also in the summary): a dialog asks for the name (the server's rule, mirrored by the page; the name of the last export is offered again, and a name already in use is announced, since the render replaces it), shows the progress with the stop button, and at the end says where the file is (`path`, relative to `WORK_DIR`, in every entry of `exports`) with the download. The button is off, with the reason, while a job runs, while the project is busy, with no valid plan and while the edits are not saved yet (the render reads the plan on disk). A render keeps the plan it read when it started: while it runs, a saved change is flagged in the summary and in the dialog, and a finished export tells when the plan changed after it.
- **Failures**: code 3 shows the CLI's message and offers `<name>.partial.mp4`; the other codes show their message and the log line; a stopped job (143) is not shown as a failure and starts again with the same name.
- **The preview of a clip** is asked for again a moment after the last change of the clip (trim, duration), so a slider makes one request, not one per step; if FFmpeg fails the player offers a retry.

## 14. States and edge cases

- **Empty or in progress**: the editor opens on an empty or populated plan; with no plan yet it shows the analysis progress.
- **Analysis incomplete** (new, changed or removed files in the folder, interrupted job): the project says so and offers "Complete the analysis". Removed files: their clips are marked as missing.
- **Ollama not available** for an analysis with AI: choice between waiting and continuing without AI (section 6). Without AI the report and the project say so.
- **Insufficient material**: the planner's warning (shorter video, with the reason) is shown with the plan.
- **Total above or below the requested duration**: the counter shows `duration / requested`; the tolerance is the one of `SPEC.md` (±5%). Outside it: a warning, not a block.
- **Element no longer in the media** (moved file): clip marked as missing, left out of the render with a warning, not removed.
- **Plan changed elsewhere** (different `revision`, e.g. a CLI run): message and a choice between reloading and overwriting (the overwritten version goes into `plan_history/`).
- **Project busy** (lock held by a CLI job): read-only until it ends.
- **Rendering in progress**: the editor stays usable; "Export" is disabled; progress bar from `status.json`; the render can be stopped.
- **Check failed** (code 3) or missing requirements (code 4): the message of the CLI, and for code 3 the `.partial.mp4` is offered for inspection.

## 16. Decisions (closed on 2026-11-14)

All approved as proposed, except D7 (React and TypeScript instead of Preact + htm) and D10 (Italian as the default language, more languages later), changed by the user. D11 is adapted to TypeScript.

**D1 — Transitions not at the edges of the clip.** The mockup lets them go anywhere; FFmpeg has no natural equivalent of a dissolve or fade in the middle of a clip. Decided: `fade_in`, `fade_out` and `dissolve` only at the edges (an effect dropped elsewhere snaps to the nearest edge); in the middle only an explicit `dip` type (to black and back), so that nothing is reinterpreted silently.

**D2 — Total duration with dissolves.** `SPEC.md` (section 8) overlaps the clips and shortens the total by the dissolve; the mockup simply adds the durations. Decided: the counter always shows the value computed by the shared function (`plan_rules`), which subtracts the overlaps.

**D3 — Limit on the duration of transitions.** `SPEC.md` imposes `d_eff = min(d, 0.25 × t_min)` on every transition; manual ones must be able to reach the edges of the clip. Decided: the 25% limit applies to the transitions with `origin: planner` (migrated v1 plans included, so nothing changes for them); for `origin: user`, "inside the clip, no overlap with the other effects of the clip, at least 0.2 s, and a dissolve inside the free space of both clips". The renderer still reduces out-of-limit transitions written by hand, with a warning, and records in the report what it applies.

**D4 — A single representation of the transitions.** Decided: `effects` replaces `transition_in` (schema v2) and the v1 plans are still read; a dissolve is stored once, in the incoming clip with `offset: 0`; the global fades from and to black become effects of the first and last clip.

**D5 — Original audio of the videos.** The "Video audio" lane needs the original audio, planned for Milestone 3, and section 1 forbids building features the renderer does not support. Decided: no lane and no `audio` block in these steps; both come with Milestone 3 (schema 3, trivial migration).

**D6 — Music with several tracks, parts and shift.** `SPEC.md` (Milestone 1) has a single track adapted to the duration. Decided: the renderer supports several tracks, parts and `offset` in U2; a single track without changes keeps the behavior of `SPEC.md` (cut with fade-out, or loop with crossfade). The plan saves the path relative to the music root (`music_dir` setting, `/music` in the compose file), so it stays valid between the development PC and the server.

**D7 — Frontend.** Decided by the user: **React and TypeScript**, with a build phase (section 4, "Frontend"). Bundler esbuild, type checking with `tsc --noEmit` and `strict`; no Vite and no development server. No other framework, component library, state library or CSS framework without a concrete reason ("How to work" in `SPEC.md`). Current stable versions, pinned exactly in U4 with their licenses.

**D8 — HTTP server.** Decided: standard library, polling, single-range `Range` implemented by hand; no framework, no SSE.

**D9 — Projects and input folder.** Decided: one workdir per input folder in `/work/projects/<slug>-<hash>/`; the choice is limited to the folders under `MEDIA_DIR` (for another tree, change `MEDIA_DIR` in `.env`). The CLI keeps `/work` as its default workdir.

**D10 — Language of the interface.** Decided by the user: **Italian by default**, other translations possible later.
- One catalog per language: `frontend/src/i18n/it.ts` is the reference. Keys and code are in English; only the values are in the language (the "everything in English" rule covers code and documentation, not the catalog values).
- The type of the messages comes from the Italian catalog, so a new language is one more file whose completeness `tsc` checks. Dates, numbers and durations are formatted with `Intl` in the catalog's locale.
- Only the Italian catalog is written now. With more than one, a language selector appears in the settings; the choice is saved in the browser, Italian when nothing is saved (no detection from the browser).
- The server returns messages in English with a code, which the interface translates; for an unknown code it shows the English message.

**D11 — Tests of the client logic.** Decided: that logic (undo history, timeline geometry, snapping, use of the limits) in pure TypeScript modules without DOM, compiled with esbuild and run with `node --test` (`npm test` in `ui-dev`). Node only in the build stage and in `ui-dev`, never in `runtime`.

**D12 — Access on multi-user machines.** On `127.0.0.1` any local user of the server can reach the editor and the photos. Decided: no authentication, a documented limit (single-user machine or a server with trusted users); if needed later, a random token generated at start and required as a cookie.

**D13 — `app` service in the `cli` profile.** With `app` outside any profile, a bare `docker compose up` would start it with no arguments, that is a full job on `MEDIA_DIR`. Decided: `app` in the `cli` profile (`docker compose run --rm app …` keeps working, because a service named explicitly enables its profile); README and launcher always name the services.

**D14 — Browser tests with Playwright.** Added at the user's request, after U5 (the first step with drag and drop, handles and focus that the static checks cannot exercise). Decided: a `e2e` service in the `dev` profile, built from the pinned Playwright image (Chromium only there, Node 24 stays out of `runtime`), with `@playwright/test` pinned in `frontend/e2e/package.json` and its lockfile (Apache-2.0). It shares the network of `nginx` (`network_mode: service:nginx`), so the page is `http://localhost:8080` and the checks of `Host` and `Origin` are the real ones; it publishes no port, mounts only the repository and has no `MEDIA_DIR`. The tests work on a synthetic vacation (`dev-media/e2e-vacation`, made by `frontend/e2e/make_media.py`) and, from U6, on two synthetic tracks (`dev-media/e2e-music`, made by the same script and given to the editor as its music root with `MUSIC_DIR=./dev-media/e2e-music`, so the editor never lists the real music folder), prepare their plan with the real analysis job (no AI) and look at the page and at the plan the server saved. They run on request (`MUSIC_DIR=./dev-media/e2e-music docker compose run --rm -T e2e npm test`), not in `scripts/test-docker.sh`, which only checks the service's configuration. Each later editor step adds its own specs.

**D15 — Single-file launcher with a Chrome window.** Added at the user's request for U8, replacing the `.desktop` file with `xdg-open`, which cannot tell when the user has finished. Decided:
- **Window**: a Google Chrome `--app` window with its own profile (`~/.config/vacation-memories/profile`), so the launcher can wait for the process and run `docker compose stop` when it ends (also on SIGINT/SIGTERM/SIGHUP). A webview (`pywebview`, WebKitGTK) was rejected: it needs GTK, WebKit2GTK and the H.264 GStreamer plugins on the host, the `<video>` with `Range` is fragile there, and the Playwright tests of D14 run on Chromium. Chrome is the only host requirement besides Docker Engine and Compose, and only for the launcher: the containers and the server do not depend on it and still open nothing. **Fallback without Chrome**: the page opens in the default browser with `xdg-open`. That gives no sign of the close, so the launcher stays running until `--stop` (menu action "Stop Vacation Memories", or SIGTERM/Ctrl+C), which stops the containers; `--stop` also stops what a launcher that was killed left up. A browser asked for with `--browser` and not found is an error, not a fallback.
- **One file**: `scripts/launcher.py` uses the standard library only and is built with PyInstaller, a **build-time tool** in the `launcher-build` service (`dev` profile, pinned in `requirements-launcher.txt`, no network at run time, the repository mounted, output `dist/vacation-memories`, never in `runtime`). The executable embeds `compose.yaml`, `compose.intel-gpu.yaml`, `compose.selinux.yaml`, `docker/nginx.conf` and `docker/compose.toml`, plus `dist_config.json` with the image repository (`IMAGE_REPO`, no default) and the version (`APP_VERSION`). At each start it extracts them into `~/.local/share/vacation-memories/<version>/`, because the bind mounts need paths that outlive the process, and runs `docker compose --project-name vacation-memories-app --project-directory … --env-file …`. It is built on an old glibc (`python:3.12-slim-bullseye`, 2.31) so it runs on older hosts too.
- **Images from Docker Hub**: `nginx` and `ollama` are public pinned images; `app` and `editor` use `${VM_IMAGE:-vacation-memories:local}` (compose default unchanged), which the launcher sets to `<IMAGE_REPO>:<version>`; it runs `docker compose pull editor` when the image is not on the machine and `up -d --no-build`. The image is published by the `publish-image` job of `ci.yml` on a `vX.Y.Z` tag, after both test jobs pass, as `<IMAGE_NAME>:<version>` (plus `latest` unless the version is a pre-release): `IMAGE_NAME` is a repository variable, `<namespace>/<image_name>` without a registry prefix, and the login uses the secrets `DOCKERHUB_USERNAME` and `DOCKERHUB_TOKEN`. The `release` job of the same workflow then builds the launcher with `IMAGE_REPO` set to the same value and attaches it, as `vacation-memories-<version>-linux-x86_64` with its `.sha256`, to the GitHub release of the tag, whose notes are the `## [<version>]` section of `CHANGELOG.md` (a missing or empty section fails the `tests` job first, so nothing is published); a version with a hyphen is a pre-release. Publishing by hand (`docker build --target runtime`, `docker push`) still works; the build service never logs in or pushes.
- **Environment variables**: asked on the first start, because a double click has no terminal, in a page served by the launcher on `127.0.0.1` (random port, token, `Host` and `Origin` checks, a CSP with a nonce, no external resource) and shown in the same Chrome window, which then goes to `http://127.0.0.1:8080`. Asked: `MEDIA_DIR` (must exist), `WORK_DIR` (default `~/VacationMemories`), `MUSIC_DIR` (optional: empty means an empty folder in the data directory, because compose binds with `create_host_path: false`), `ASSUME_TZ`, `OLLAMA_MODEL`, and the Intel GPU and SELinux overrides, pre-filled from `/dev/dri` and `/sys/fs/selinux/enforce`. Computed: `HOST_UID`, `HOST_GID`, `APP_VERSION`, `VM_IMAGE`. The answers are saved in `~/.config/vacation-memories/answers.json` and written for compose to `compose.env` (mode 0600); the repository's `.env` is never read or written. `--reconfigure` (and the menu action) asks again.
- **Not decided here**: the Docker Hub namespace and image name, which are the user's (the `IMAGE_NAME` variable).
